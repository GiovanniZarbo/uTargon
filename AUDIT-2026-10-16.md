## 1. 🔴 Bug di build attivo (P0)

### Sintomo (dal log che hai incollato)

```
Failed to parse json from https://schema.blue-build.org/modules/install-icons-latest.json
→ <html lang="en"> ... (pagina indice, non JSON)
value is not valid under any of the schemas listed in the 'anyOf' keyword
Recipe ./recipes/recipe.yml failed to validate
```

La CLI di BlueBuild non riconosce `type: install-icons` come modulo locale: cerca di scaricarne lo **schema remoto** dal server di BlueBuild, che risponde con una pagina HTML (il modulo non esiste lì) → parse fallito → validazione della recipe fallita → **exit 1, l'immagine non viene costruita**.

### Causa radice

Discrepanza tra documentazione e CLI in uso (`blue-build/github-action@v1.13`):

- La [reference dei moduli](https://blue-build.org/reference/module) dice che la sorgente di default è "ibrida" (repo ufficiale + cartella `modules/` locale) e che **non serve** dichiarare nulla.
- Ma l'help della CLI nel tuo log dice testualmente: *"If you're using a local module, be sure to add `source: local` to the module entry"* — e senza di esso prova lo schema remoto e fallisce.

Nota anche i log `Searching /modules/2` / `/modules/3`: la CLI **trova** le cartelle locali, ma la validazione della recipe non le accetta senza la dichiarazione esplicita.

### Fix proposto (da applicare quando vuoi — NON applicato in questo audit)

```yaml
  - type: install-icons
    source: local
  - type: install-cursors
    source: local
```

2 righe in `recipes/recipe.yml`. Se anche con `source: local` la validazione fallisse, il fallback garantito è tornare al modulo standard `type: script` (che è nella lista schemi ufficiali come `script-v2.json`) mantenendo gli script in `files/scripts/` — ma prova prima `source: local`, che è la strada corretta e quella raccomandata dal tuo stesso errore.

## 3. Report ottimizzazione: quanto pesano gli script?

### 3.1 Script di build (modules/)

| Script | Cosa fa | Peso | Verdetto |
|---|---|---|---|
| `install-icons.sh` | Scarica Fluent pinnato a commit, installa **tutte** le 9 varianti colore (`install.sh -a`) | Download ~10-20 MB; disco: il grosso è il tema base, le varianti ereditano e aggiungono poco | **Necessario**: il cambio variante dinamico (rofi-wallpaper/matugen) richiede tutte le varianti. Non è grasso inutile |
| `install-cursors.sh` | Scarica ArcDusk pinnato, `./install.sh` **senza argomenti** → installa tutte le varianti del repo | Stima: 10-30 MB a seconda delle varianti | ⚠️ **Unico risparmio concreto**: usi solo `ArcDusk-cursors`. Passare il nome a `install.sh` (es. `./install.sh ArcDusk`) installerebbe una variante sola. Da quantificare sull'immagine (comandi §3.4) |
| ~~`fix-permissions.sh`~~ | — | — | ✅ **Eliminato** in `d5774e1`: era 1 step di build a ogni run (2 chmod + symlink); ora il bit eseguibile viaggia nel commit, costo zero |

Osservazioni: i due download a ogni build quotidiana sono inevitabili senza cache, ma GH runner ha banda abbondante e i tarball sono piccoli; il pin SHA rende il tutto riproducibile. `set -euo pipefail` fa fallire il build su errore reale (giusto per una distro).

### 3.2 Script runtime

| Script | Frequenza | Peso | Verdetto |
|---|---|---|---|
| `utargon-first-setup` | 1 volta per utente (flag + retry se il desktop non è su) | Leggero: 1 chiamata LnF, 1 wallpaper, 2 qdbus script, 5 kwriteconfig6, 1 colorizer check. Worst case ~25 s di attesa polling | ✅ Sano. Le operazioni sono idempotenti e non bloccanti (`(cmd &)`) |
| `rofi-wallpaper` | On demand (Super+W) | ⚠️ prima di questa settimana il blocco Python/PIL calcolava la HSV a ogni lancio; ora rimane solo scansione cartelle + `matugen` (Rust, <1 s) | ✅ Il refactor "matugen unico motore" ha tolto il pezzo più pesante. La scansione è O(file) banale |
| `fluent-folders.sh` (post-hook matugen) | A ogni cambio wallpaper | 1 kwriteconfig6 + 1 gsettings + rm cache + 1 qdbus | ✅ Minimo indispensabile (vedi però sospetto 2.2 sul no-op) |
| `fastfetch.sh` (profile.d) | Ogni shell interattiva | ~50-100 ms | ✅ Accettabile per una desktop distro |

### 3.3 Processi residenti (il vero costo continuo)

| Processo | Costo | Note |
|---|---|---|
| `kde-material-you-colors` (demone) | Processo Python residente, tipicamente ~50-100 MB RAM | **L'unica voce continua** dello stack theming. È il prezzo del cambio colori automatico a ogni wallpaper — voluto. Matugen invece è one-shot, zero costo residente |

### 3.5 Verdetto complessivo

**Gli script non sono inutilmente pesanti.** Dopo i refactor del 14-16/10 (eliminato il doppio motore colore Python, unificata la config in 3 fonti, eliminato fix-permissions, demone KMYC unico residente) la stack è asciutta. I due unici margini concreti, entrambi opzionali:

1. **ArcDusk: installare solo la variante usata** (risparmio disco immagine, da misurare).
2. **Compressione asset** (~2,5 MB).

Il vero "peso" dell'immagine resta dove non puoi agire con gli script: base Kinoite + Flatpak di sistema.
